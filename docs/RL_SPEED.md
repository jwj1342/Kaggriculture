# RL 训练为什么慢，时间花在哪，怎么加快

这份文档只谈 **墙钟速度**（同样硬件上，一小时能采多少局、能做多少次策略更新），
不谈「怎样更容易赢」。训练算法、奖励、课程见 `docs/RL_TRAINING.md`。

一句话结论：

> 慢的不是神经网络，也不是 CPU 核不够。慢的是 **官方对局框架每走一步就把整盘棋复制两遍**。
> 把模型单独放到 GPU 上几乎不加速；加核只能线性摊开复制成本。真正的加速是 **少复制、一次推很多局、少打废局**。

---

## 0. 先看一次真实训练花了多久

2026-08-16 在本机跑的官方引擎 PPO（`rl/train_ppo.py`，`rl/ckpt_official/`）：

| 项 | 数字 |
|---|---|
| 配置 | `--arch multi --iters 300 --episodes 8 --workers 8` |
| 一局长度 | 720 步（比赛完整赛季） |
| 每一轮墙钟 | 大约 **9–15 秒**（8 局并行） |
| 300 轮合计 | **约 50.5 分钟**（3033 秒） |
| 采到的局数 | 300 × 8 = **2400 局** |
| 环境步数 | 约 2400 × 720 ≈ **170 万步** |

每一轮的日志里，`time=` 几乎等于「8 个进程各打完一局」的时间。后面的 PPO 更新（根据这 8 局的数据改权重）只占其中很小一块。所以优化更新算法、换 Adam 参数、把 MLP 变瘦，**都动不到这 10 秒**。

## 1. 几个必须先懂的词

这些词在后文会反复出现，这里按「它对速度意味着什么」来解释。

**引擎 / interpreter**
游戏规则的实现：根据当前棋盘和双方动作，算出下一帧棋盘。本仓库的权威副本是 `reference/engine/kaggriculture.py`。提交到 Kaggle 时，评测用的是同一份规则。

**框架（kaggle-environments）**
套在引擎外面的壳：负责加载两个 agent、检查动作格式、把观测交给双方、记录回放。训练时我们走的是 `env.train([None, opponent]).step(action)`。壳比引擎贵。

**deepcopy（深拷贝）**
把一整份游戏状态（棋盘、仓库、工人、市场、随机数……）复制成一份互不影响的新对象。Python 里这是按对象图递归拷贝，棋盘越大越慢。框架每一步对 **每个 agent 各拷一次**，所以一步拷两遍。目的是：两个 agent 不能偷偷改同一份棋盘。对锦标赛这是对的；对「两边都是我们自己的训练进程」这是浪费。

**jsonschema**
用一份格式说明书检查每个动作字典写得对不对。非法动作在本游戏里本来就是静默无效（不报错、不扣分），所以训练和本地评测可以关掉它。环境变量 `KG_FAST_ENV=1` 就是干这个，大约再快 **17%**，结果与开着时逐字节相同。当前训练脚本已经默认打开。

**rollout（滚出 / 采样）**
让当前策略实际去打若干局，把「看到什么、做了什么、得到什么奖励」记下来。PPO 必须先有这些轨迹才能更新。我们的墙钟几乎全花在 rollout 上。

**PPO**
一种策略梯度算法：用刚打的几局数据，小步更新网络，使高奖励的动作以后更常出现。更新本身是矩阵运算，8 局 × 720 步的数据量很小，所以它不是瓶颈。

**batch / 向量化**
一次对 **B 局**做同一条运算（例如 B=256），而不是 for 循环打 256 次。GPU 和现代 CPU 都擅长这种「同样的公式、很多份数据」。官方引擎是一份 Python 对象一局，没法向量化。

**bit-exact（逐位一致）**
两套引擎对同一串双方动作得到完全相同的下一状态。`rl/gpu/` 用官方录音重放对拍（`python -m rl.gpu.verify`）：杂草/商店用同一条 `Random((seed * 1_000_003) ^ day)`，雇工出生点、日结仓库溢出、未浇水变杂草的字段清理都按 interpreter 修过。`starter` vs `starter` 和 `barnyard.py` vs `starter` 在种子 7/13/42 上金钱、商店、棋盘、仓库一致。仍有固定上限（引擎最多 16 个 hand；官方不封顶）。**训练日志里的 win rate 仍然不能当天梯分数**——GPU 环境的对手是向量化 starter/scripted，不是 `barnyard.py` 文件；提交仍走官方 interpreter。这个仓库里，「按规则推出来但引擎差一点」的改动，七次里有四次仍然输了。

**课程学习（curriculum）**
先打弱对手（`starter`），会种地了再打强对手（`barnyard`）。弱对手阶段的 720 步完整赛季，很多步只是为了「学会浇水」，用满赛季去买这些经验很亏。

**IDLE 回退**
网络某个单位输出「什么都不做」时，解码器会走一套写死的默认农活（接近 barnyard 风格的调度）。所以即使网络很弱，农场也不会完全空转。这不影响速度，但解释了「为什么慢也在赚钱」。

## 2. 一局里时间到底花在哪

数字来自本仓库对 **官方对局** 的剖析（`docs/CONTRIBUTING.md`、`docs/VALIDATING.md`），不是猜的。一局大约 2.6–3.2 秒（单核、已开 `KG_FAST_ENV` 时约 2.6 秒）：

```
一步的真实路径（当前训练）：

  策略网络前向（numpy MLP，batch=1）     ← 很小
  解码成引擎动作字典
  对手（starter 或 barnyard.py）再算一套动作
  框架：deepcopy 状态  ×2               ← 约 42%
  框架：jsonschema 校验动作             ← 约 12%；KG_FAST_ENV 可去掉
  引擎 interpreter 真正改棋盘           ← 其余里的一块
  特征编码 + 势函数奖励
```

按整局墙钟粗分：

| 部分 | 大约占比 | 训练里能不能省 |
|---|---|---|
| `deepcopy` 整盘状态，每步两次 | **~42%** | 能。训练双方都在我们进程里，不必为隔离而拷 |
| `jsonschema.validate` | **~12%** | 已省。`KG_FAST_ENV=1` |
| 被测策略（我们的 MLP + 解码） | **~13%** | 省不了多少；再瘦网络几乎无感 |
| 对手 agent + 引擎本身 + 其它 | 其余 | 对手越复杂越贵；引擎可换成张量版 |

把 75→256 的 MLP 搬到 GPU、每次只送 1 个观测，**会更慢**：一次 GPU 调用的启动开销大于这点计算。GPU 只有在「一次送进几十、几百份状态」时才划算。

加 CPU 核能让 8 局同时打，墙钟从「8 × 2.6 秒」变成「约 2.6 秒」（外加进程开销）。再往上加，你只是用更多核去 **并行做同样的 deepcopy**。所以「只加核」不是错误，是收益递减，而且不是这篇要解决的问题。

## 3. 瓶颈清单（按对墙钟的影响排序）

### 瓶颈 A — 框架每步深拷贝（最大）

**现象：** 8 进程打满，一轮仍要约 10 秒，因为每个进程内部仍然在 720 步 × 2 次拷贝。

**原因：** `rl/env.py` 使用 `kaggle_environments` 的 `env.train().step()`。这是提交/评测的正确 API，不是训练的最快 API。

**不解决的后果：** 怎么调 PPO、怎么加核，一轮都很难掉到「环境步成本」以下。

### 瓶颈 B — 一局必须走完 720 步

**现象：** 日志里 `steps=719.0`，几乎每局都打满。前期对 `starter` 学「种胡萝卜、浇水」，并不需要打完 30 天。

**原因：** 环境按比赛规则默认 `episodeSteps=720`。训练脚本没有「短局课程」。

**后果：** 同样学会浇水，你付了完整赛季的 deepcopy 账单。2026-08-16 那次，前 100 轮对 `starter` 大约花了 **17 分钟**，只是为了把种地学到能赚钱。

### 瓶颈 C — 采样无法向量化

**现象：** 官方引擎状态是嵌套 Python 字典（棋盘格子、工人列表……），一次只能推 **一局的一步**。

**原因：** 规则实现是为「两个提交文件对打」写的，不是为「256 局同时种地」写的。

**后果：** 有 GPU 也喂不饱。必须先把状态收成固定形状的数组/张量（`rl/gpu/` 做的就是这件事）。

### 瓶颈 D — 强对手本身很贵，而且每步都跑

**现象：** 切到 `barnyard.py` 之后，一轮时间仍在 9–15 秒量级（有时略慢），因为 deepcopy 仍在，另外还要跑一个大型规则 agent。

**原因：** 训练循环里 **每一步** 都调用完整对手。课程切过去之后，70% 的局打 barnyard、30% 仍打上一档（`mix_prev=0.3`）。

**后果：** 你用最贵的对手去提供「还打不赢」的信号。监督信号可以更便宜：冻结一份自己的旧权重当对手，隔一段时间再用官方引擎对 barnyard 做 h2h 验收。

### 瓶颈 E — 每局重建环境、每局把权重 pickle 进子进程（次要）

**现象：** worker 每次 `run_episode_worker` 都 `make()` 一个新环境，主进程把整份 `weights_dict` 序列化后传进去。

**原因：** `ProcessPoolExecutor` 的任务参数必须能 pickle；环境对象没有在 worker 里长期复用。

**后果：** 相对 2.6 秒一局，这通常是小头。值得修，但不要指望再快一倍。修好之后，瓶颈 A/B/C 仍然在。

### 瓶颈 F — 从零（IDLE 先验）在官方引擎上把「会种地」和「打 barnyard」绑在一次 300 轮里

**现象：** 50 分钟里大约 1/3 用来打 starter，2/3 用来打 barnyard，后者 `ep_reward` 长期为负，h2h 仍是 0 胜。

**原因：** 官方引擎太贵，不该用来买「从不会种到会种」这种弱对手经验。

**后果：** 同样 50 分钟，如果种地阶段用张量引擎跑完，官方时间可以全部留给 barnyard。

## 4. 对应的解决办法

每一条都写清：**改什么、快多少、会不会改游戏规则、验收标准**。

### 方案 1 — 训练时绕开 `env.train()`，直接调官方 interpreter（规则仍真）

**做什么：** 新写一个训练专用 env：持有一份可变的引擎 state，双方动作在喂进去之前各自浅拷/深拷 **动作字典**（很小），不要拷整盘棋。重置时才 clone 一份初始局面。权威实现仍是 `reference/engine/kaggriculture.py`。

**预期：** 去掉约 42% 的 deepcopy 之后，单核一局从 ~2.6 s 降到大约 **1.4–1.8 s** 量级（1.5–2×）。8 进程一轮从 ~10 s 降到大约 **5–7 s**。300 轮从 50 分钟降到大约 **25–35 分钟**。这是粗算，落地后要用同一 seed 对拍。

**规则：** 仍是官方规则，仍能加载 `barnyard.py`。

**必须验收：** 同一 `(seed, 双方动作序列)` 下，与 `env.train()` 路径的终局金钱、棋盘一致。不一致就停，不要「差不多」。

**这是官方微调阶段必做的。** 单独做不够数量级，但结论可以信。

### 方案 2 — 张量引擎一次推很多局（大约 10–50× 采样）

**做什么：** 已有代码 `rl/gpu/`。状态做成固定形状张量，一次 `step` 更新 B 局（建议先 B=64，有 CUDA 再 B=256）。对手只能是向量化的 `starter` / `scripted`（全部 IDLE + 默认调度），**不能**直接跑 `barnyard.py`。

**预期：** 即便没有 GPU，CPU 上 B=64 的向量化也比「8 进程 × 官方 deepcopy」高一个数量级。有 CUDA 再换 GPU 版 PyTorch（`pip install torch --index-url https://download.pytorch.org/whl/cu124`）。当前本机若 `torch.cuda.is_available()` 为 False，装的是 CPU 轮子，换轮子才会用到卡。日结杂草仍按官方 RNG 在 Python 里逐格抽，B 很大时日结会比纯张量慢一截，但相对 deepcopy 仍是小头。

**规则：** 录音重放应对齐。对拍命令：

```bash
python -m rl.gpu.verify --seeds 7,13,42 --left starter --right starter
python -m rl.gpu.verify --seeds 7,13,42 --left agents/barnyard.py --right starter
```

标准：双方金钱到美元、商店解锁序列、棋盘 kind/动物/作物/产量、0 号仓库。第一次分叉的 step/字段就是下一个要修的 bug。

**必须验收：**

1. `python -m rl.gpu.selfcheck` 通过。
2. 上面的 `verify` 在你在意的对手上绿。
3. 导出后 **必须** 用官方引擎 `eval.py h2h` 对 `barnyard`。只有这边的胜率算数。
4. 不要把 GPU 日志里的 `ep_reward` / `win=` 写进梯子结论。

**集群锦标赛仍然不要申请 GPU。** 那是 deepcopy 负载；这套脚本是本机 / 带卡机器的训练路径。

### 方案 3 — 短局课程：先 240–360 步，会种了再 720（大约 2–3× 前期墙钟）

**做什么：** 对 `starter` 的若干轮使用更短的 `episodeSteps`（例如 10–15 天），势函数已经在「种下即得分」，不需要把赛季打完才有梯度。对 barnyard 的微调改回 720，因为胜负在赛季末。

**预期：** 种地阶段墙钟大约除以 2–3。2026-08-16 那 17 分钟 starter 段可以压到大约 6–8 分钟。

**规则：** 短局的最优策略不一定等于满局最优（末期倾销、雇工节奏会变）。所以短局只用于课程前期，满局微调不能省。

### 方案 4 — 从已有 checkpoint 续训，官方时间只打强敌

**做什么：** `--init-weights rl/ckpt_official/ppo_it0300.npz`。那份权重对 barnyard 已经能赚大约 **$27k 中位**（v1 是 $0），不要从 IDLE 再买一遍种地。

**预期：** 省掉整个 starter 课程的墙钟（那次是约 100 轮 / 17 分钟），把预算全部给 barnyard。

**规则：** 不变。这是样本效率，不是逐步变快。

### 方案 5 — 训练对手用便宜替身，barnyard 改成定期考试

**做什么：** 日常 rollout 的对手用：冻结的旧策略（self-play）、或 `scripted`、或 `starter`。每隔 N 轮（例如 10 轮）才导出，用官方引擎对 `barnyard` 打一组 h2h（哪怕 8–16 seed）看有没有赢面。

**预期：** 每步少跑一个大型 Python agent；更重要的是心理和时间分配——不要用「训练日志里对 barnyard 的负回报」代替考试。

**规则：** 训练分布会偏离「只打 barnyard」。所以考试必须是官方 h2h，不能省略。

### 方案 6 — worker 复用环境、权重共享内存（大约 10–20%，官方路径的扫尾）

**做什么：** 每个子进程启动时 `make()` 一次，后面只 `reset(seed)`；权重放到 `multiprocessing.shared_memory` 或依赖 fork 的 copy-on-write，避免每局 pickle 整网。

**预期：** 小。在方案 1 之后做。不要指望它单独改变数量级。

## 5. 明确不要做的事

| 做法 | 为什么无效 |
|---|---|
| 只加 `--workers` | 每个 worker 内部仍在 deepcopy；核数线性摊开同一笔账。本机 8 核已经把 8 局并行打满一轮墙钟 |
| 把 MLP 单独放到 GPU，每次 1 个观测 | 启动开销 > 计算；瓶颈根本不在矩阵乘 |
| 集群训练作业申请 GPU | 官方对局是单线程 Python + deepcopy，卡在空转 |
| 只在 `rl/gpu` 上看到 win rate 就提交 | 对手是向量化 scripted，不是 `barnyard.py`；必须官方 h2h |
| 为了快把 `episodeSteps` 永远留在 240 | 末期倾销和 30 天规划会学歪；满局微调省不掉 |
| 关掉 deepcopy 却不对拍 interpreter | 静默规则分叉，看起来在加速，学的是另一款游戏 |

## 6. 推荐落地顺序（两阶段，不是二选一）

把「快」和「真」拆开：快的阶段买农活，真的阶段买能否赢 barnyard。

```
阶段 A  大量采样（快，规则已对拍）
        rl.gpu.train  B=64 或 256
        对手 starter → scripted
        初始化：rl/ckpt_official/ppo_it0300.npz（已经会赚钱）
        目标：导出后在官方引擎上对 starter 稳定大胜，金钱继续高于 ~27k

阶段 B  短微调（慢一点，规则真）
        官方 interpreter，无框架 deepcopy（方案 1）
        对手 barnyard + 少量冻结自身
        满 720 步
        目标：eval.py h2h vs barnyard，至少 48 seed × 2 座位

阶段 C  验收（不能省）
        python tools/eval.py h2h agents/rl_agent.py agents/barnyard.py --seeds 48 -j 8
        python tools/stress.py agents/rl_agent.py -j 8    # 必须 28/28
        只有这里的胜率可以写进结论
```

时间直觉（同一台 8 核机器，粗算）：

| 做法 | 大约墙钟 | 得到什么 |
|---|---|---|
| 现状：官方 deepcopy × 300 轮 × 8 局 | 50 分钟 | 会赚钱，对 barnyard 0/96 |
| 只做方案 1 | 约 25–35 分钟 / 300 轮 | 同样预算能多跑近一倍官方局 |
| 阶段 A GPU/向量化几百轮 + 阶段 B 官方 100 轮 | A 可能十几分钟量级，B 约 10–15 分钟 | 种地用对拍过的张量引擎买，赢负用真对局买 |

具体倍数以落地后的 profiler 为准；上表用来排优先级，不用来写论文。

## 7. 怎么判断「已经变快了」

不要看 `ep_reward`。看这三个数：

1. **环境步 / 秒**（所有 worker 合计）。现状大约 8 × 720 / 10 s ≈ **570 步/秒**。方案 1 若到 1000+ 就算成功；方案 2 若到 5000+ 才像向量化在干活。
2. **官方 h2h 对 barnyard 的胜场**（48 seed × 2 座位）。这是策略质量，不是速度，但阶段 A 之后必须测，以免「更快地学错游戏」。
3. **一局终局金钱分布**（中位数、最低值）。用来确认没有退回 v1 的「中位 $0 躺平」。
