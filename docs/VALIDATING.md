# 我的 agent 真的更好吗？—— 精简版

写这份文档，是因为这个项目已经在两端各犯过一次同样的错：一个**什么都打得过**的参考场地，
和一个**什么都以同样幅度打得过**的参考场地。两者都会产出自信满满、却毫无意义的数字，
而且**都不会自己报错**。

如果只读一节，读第 1 节。**如果只记一条原则：只比较同一场地、同一 seed、同一席位的
配对结果，而且本地结果不外推天梯。**

## 本地固定场地 A/B：先看胜负，再看 margin 与行为

面板胜率是固定对手场内的首要结果，适合判断一次改动是否移动了本地策略；它不是跨场的
绝对强度，也不能预测天梯。RL 的长期决策实验还必须同时报告配对 margin、目标行为读数
和 held-out 对手，具体门槛见 `rl/TODO.md`。

**面板（panel）**：一组**固定不变**的对手。当前用 `agents/wrapped/` 里的十个：
`w39 w48 w16 w68 w56 w25 w12 w28 w05 w02`。固定，是为了让不同候选之间可以比较 ——
换了对手，两个数字就不再是同一把尺子量出来的。

**面板胜率**：把候选放进这个面板，跨多个随机种子、**双方交换先后手**各打一遍，赢的比例。

```
10 个对手 × 96 个种子 × 2 个座位 = 1,920 局
```

```bash
sbatch --array=0-15 --cpus-per-task=32 --mem=40G --time=00:30:00 \
    slurm/tournament_array.sh panel \
    --agents <你的候选>.py \
    --panel agents/wrapped/w39.py agents/wrapped/w48.py agents/wrapped/w16.py \
            agents/wrapped/w68.py agents/wrapped/w56.py agents/wrapped/w25.py \
            agents/wrapped/w12.py agents/wrapped/w28.py agents/wrapped/w05.py \
            agents/wrapped/w02.py \
    --seeds 96 --label <名字>
```

1,920 局的二项误差约 ±0.5–1.2 个百分点，所以**差距小于 3 个点就当没有差距**，
除非区间不重叠。

### 为什么是胜率，不是钱

**这个比赛只看输赢。** 名次由「赢了多少局」算出（Bradley-Terry），钱只在同一局内部
用来判定谁赢。所以**胜率就是比赛真正评的那个量**，而任何以「钱」为单位的指标都只是
代理指标 —— 代理指标会背叛你。

具体地，剧本库里每条线都带一个 `best_score`（录下它的那一局，那位选手赚了多少钱）。
**它看起来像质量指标，但不是，不要用它挑线。** 2026-08-13 实测，同一支队伍的 17 条线：

```
best_score  vs  面板胜率      spearman −0.47      <- 负的
```

原因是它测的根本不是选手。同一局里，**两位选手赚的钱几乎完全一起动
（`pearson +0.950`）** —— 它测的是「那盘棋有多富」（商店抽到什么、镇上需求多大），
不是「谁打得好」。用它挑线，等于按「卷子简单」挑学生。

而且它是 **n=1**：371 条线里 314 条只被录到过一次，所以那个数字背后没有分布，
多取几局求平均也救不了 —— 那只会得到「这些棋盘平均有多富」。

> 代价是实打实的：`submissions/2026-08-13-topline/` 就是按 `best_score` 挑出来的
> （17 条里第 1），而它的面板胜率只排**第 7**（92.4%，第一名 `k06` 是 98.5%）。

### 面板胜率还没解决的两件事（09-02 起：第 2 条已升级为上面那条硬结论）

不要把它当成已经校准好的尺子：

1. **它只是对那固定十个对手的均值。** 这个空间**非传递**（3.3% 的三元组构成环），
   换一批面板，名次可能变。
2. **它不能预测天梯，连同队内挑录音也失败。** 跨队本地胜率与源队伍天梯分零相关
   （`spearman −0.05`, n=100，见 §1 的方框和 `ROADMAP.md` §10.5）。同队前瞻实验中，
   面板选 k06（98.5% vs 92.4%），早期天梯读数曾看似通过；等到收敛，k06 2035.9、
   k01 2302.2，方向排反 266.3 分。768 局直接对打也同样挑错。最终判词见 `RUNS.md`。

它是**固定场地内做本地 A/B 的工具**，不是天梯代理目标。区别很重要。

## 3. 怎么读结果

**报两个数字，不是一个。** 那批带外包装的参考 agent 对引擎级的 agent 而言是打不过的
（我们赢 0.2%）。把它们平均进一个总胜率里，只是加了一个常数：十五个对手里有三个打不过，
等于给每个分数压了约 25 分 —— 所谓「43%」的真实含义是「对能打的对手 73.5%，对三个
打不过的 0%」。

**胜率饱和时读中位收入。** 在终局窗口扫描里，八个臂的幽灵胜率完全相同，而中位收入把
它们正确排了序，和那个没饱和的场地结论一致。

**非单调的曲线不是结论。** 它说明你扫的那个变量不是真正起作用的变量。第一次终局窗口
粗扫给出 95.6 / 98.6 / 89.8 / 94.1 / 85.1 —— 中间那个凹陷就是"该加密再扫"的信号，
而加密后的扫描找到了一个干净的平台。

**检查镜像对局。** 让候选和它自己打。分数大致减半；如果减得比一半还多，说明这个 agent
依赖一个消极的对手。

## 4. 三种「自信地得出错误答案」的方式

**重放没有逐分验证。** 任何重放录制轨迹的工具，验收标准是**复现原局双方分数到个位、
且商店解锁序列一致**：

```bash
python tools/tracelib.py verify --dates 2026-08-11 --limit 4
```

不能用「幽灵跑出一个合理的分数」当验证。`steps[i]["action"]` 是**产生**
`steps[i]["observation"]` 的那个动作，所以重放时 step `i` 要返回 `_TURNS[i+1]`；
错位一帧的重放**仍然跑出一个完整、合理的赛季**，当时 `verify` 报「达到原始分 114%」
被读成了成功。代价：一个真实排名 64/101（36.5%）的 agent 在本地读出 92.4% 第一名，
并据此提交。

**框架静默地跑了另一份代码。** `get_last_callable` 返回的是
`[v for v in env.values() if callable(v)][-1]` —— 模块字典里**最后一个 callable 值**。
包装一个 agent（`_INNER = agent`，然后重新 `def agent`）会让 `_INNER` 排在最后，于是
框架加载的是**未包装**的那个；这时每个臂分数完全相同，而漂亮的结论是"这个改动毫无价值"。
在 `agent` 之后放一个辅助 `def` 会造成同样的后果。把 callable 存进列表、用 `del` 删掉
辅助名字，然后**向加载出来的函数问一个你已知答案的问题来验证** —— 能编译不等于对。
`tools/hybrid.py:_verify` 就是这个模式。

**引擎是对的，是你读反了。** 一个探针显示农场十天没买种子、现金只有 $109–$435，看起来
像死锁。"修好"它在 137,644 局下损失 8–14 分：那些现金流向了牲畜，而牲畜更值钱。代码里
没有任何地方写着这件事 —— 它是一个现金下限和一个购买速率限制撞在一起的产物。
**在判定引擎坏掉之前，先查清楚它把资源花到哪去了。**

## 5. 同名的构建

`short(path)` 取的是**文件名**，所以两个都叫 `smallhold-crew-mgtight-…` 但来自不同
目录的构建，会在数据库里合并成同一行评分。已经有两次跑数因此报废。

对于臂之间同名的 A/B —— 所有引擎消融实验都是这样 —— 直接读分片 JSONL 并按完整路径分组，
**不要 ingest**（分片文件由 `--shard` 模式产生，别人在集群上跑完给你的也是这个格式）：

```python
import glob, json, collections, os
w = collections.Counter(); g = collections.Counter()
for s in glob.glob("data/shards/<label>/shard-*.jsonl"):
    for line in open(s):
        r = json.loads(line)
        for i, side in enumerate(("left", "right")):
            a = r[side]
            if "/bench3/" in a or "/ref/" in a:      # 这是陪练，不是候选
                continue
            g[a] += 1                                 # 完整路径，不是文件名
            w[a] += (r["money"][i] > r["money"][1-i]) or \
                    0.5 * (r["money"][i] == r["money"][1-i])
for a in sorted(g, key=lambda k: -w[k]/g[k]):
    print(f"{100*w[a]/g[a]:5.1f}%  {a}")
```

## 1. 天梯实际在给什么打分

只有**胜 / 负 / 平**。金额差距完全不进入评分。最终排行榜是对最后两周所有对局做一次
**Bradley-Terry** 拟合（[主办方确认](https://www.kaggle.com/discussions/kaggriculture/731587)）。

对本地评估的三个后果：

1. **平均收入是错误的头条指标。** 一个稳定进账 8 万的 agent，胜过一个平均 10 万但偶尔
   崩盘的。优化胜率；收入只作为诊断量报告。
2. **方差是成本，不只是误差棒。** 评分奖励的是一致性。
3. **本地排名要用和奖金同一个估计量。** `tools/tournament.py` 在本地循环赛上做
   Bradley-Terry 极大似然拟合（`tools/stats.py`），所以本地排名在**种类上**可与
   真实排行榜比较，而不是与一个沙盒平均值比较。

## 2. 关于这个环境随机性的实测事实

全部对照已安装的 1.32.6 引擎验证过。

### 2.1 给定 `(种子, 双方 agent)`，对局是确定性的

同一对 agent 在同一个种子上重跑，会精确复现那一局。所以**同一配置重复跑不增加任何信息**
—— 全部方差都活在种子之间。一个把同样配置在同样种子上跑两次的框架是在烧 CPU。

有用的推论：league 曾把 `barnyard`、`barnyard__TARGET_COWS_10` 和
`barnyard__HAND_CAP_14` 正确地评为**逐位相同**（相同 BT 强度、相同中位、相同胜率），
因为那些覆盖值恰好等于默认值。这是对整条流水线的一次免费自检。

### 2.2 共同随机数**不能**控制这个环境

这条很容易搞错。在 `_end_of_day` 里，一个由 `(seed, day)` 播种的 RNG 被**同时**用于
杂草生成和商店解锁 —— 而杂草生成在**双方**农场上每个空地消耗一次抽取：

```python
rng = random.Random((seed * 1_000_003) ^ day)
for player_id, farm in enumerate(obs0.farms):
    ...
    _spawn_weeds(farm, board_size, weed_chance, rng)   # 抽取次数 ∝ 空地数
...
town["unlocked_shops"].append(rng.choice(sorted(SHOPS)))
```

所以**你怎么打会改变哪些商店解锁**，你的**对手**怎么打也会。在一个固定种子（42）上实测，
四种对阵产生了四个完全不同的商店序列：

| 对阵 | 解锁的商店 |
|---|---|
| `pass` vs `pass` | FARMERS_MARKET, PET_CAFE, YARN_STORE, YARN_STORE, … |
| `starter` vs `starter` | ICE_CREAM_SHOP ×3, YARN_STORE, BAKERY, … |
| `barnyard` vs `starter` | ICE_CREAM_SHOP, PET_CAFE, FARMERS_MARKET, BAKERY, … |
| `barnyard` vs 自己 | BRUNCH_SPOT ×3, BAKERY, SMOOTHIE_SHOP, … |

含义：

- 按种子配对能降低方差，但**抵消不了**。你不能把商店抽样当成一个外生的控制变量。
- 一个配置改动可能因为与它自身优劣无关的原因赢下一个种子 —— 它挪动了杂草数量，
  于是抽到了更好的商店。
- **对着弱对手得出的结果不可迁移。** 换对手改变的是你自己的经济，不只是那个比较。

### 2.3 面对真实对手，分数大致减半

| 对阵 | `barnyard` 中位 |
|---|---|
| vs `starter` | 约 67,000 |
| vs 自己，以及在混合联赛里 | 约 30,000–40,000 |

两个玩家在抽干同一个市场。任何对着消极对手测出来的数字都是虚高的；
**永远同时报告有对抗的那个数字。**

### 2.4 座位在构造上是对称的 —— 但还是要验

四个象限相对棚子几何全等，各自拥有一个棚子出入格，而市场订单对双方报的是同一个
提交前库存。不存在结构性的座位优势。这里每个框架仍然会打两个座位并报告拆分结果，
因为验证这个假设很便宜，而它错了会很贵。

## 5. 到底要跑多少局？

对于二元胜负结果，在 95% 置信度下分辨出真实胜率 `50% + d` 大约需要
`n = (1.96² × 0.25) / d²` 局：

| 你想检出的效应 | 局数 | 种子（双座位） |
|---|---|---|
| 10 分（60% vs 50%） | 96 | 48 |
| 5 分 | 384 | 192 |
| 3 分 | 1,068 | 534 |
| 1 分 | 9,604 | 4,802 |

吞吐：带 `KG_FAST_ENV=1` 时**每核每秒约 0.375 局**，所以 8 核笔记本上一次有效力的
5 分测试约 4 分钟。规模换算见 `docs/VALIDATING.md` §2。

**在这里没有理由做一个统计效力不足的实验。** 这个项目最初那些 3–4 种子的扫描，
分辨的是零。

有两个办法比裸数胜场更好：

- **用收入差作为统计量。** 在一对一里，差额的符号**就是**胜负，所以它携带同样的信息
  而方差低得多。`eval.py` 会同时给它做 bootstrap。
- **按种子配对。** 两个候选在同样的种子上打同样的对手。即使 §2.2 说明它抵消不了一切，
  这仍然有帮助。

## 6. 推荐工作流

1. **一次只改一件事。** 优先做成 `tools/registry.py` 里的一个原子选项，这样它有名字、
   能被生成、而且和其他一切共用同一条执行路径。
2. **先 `stress.py`。** 28 个配置，不到一分钟，在你花掉算力之前抓出崩溃和慢回合。
3. **跑够局数。** 24 个种子够第一眼看；任何小于 10 分的结论要 96+。
4. **读胜负矩阵，不只读排名。** 一个除了某一个对手之外什么都赢的 agent，
   在告诉你一件很具体的事。
5. **检查镜像对局。** 让候选和自己打。分数减半；减得比一半还多，说明它依赖消极对手。
6. **任何意外都去 `trace.py`。** 静默空操作意味着 bug 看起来像"策略差" ——
   这个仓库里每个五位数级别的 bug 都是靠读逐日 trace 找到的，不是靠盯最终分数。
7. **在两个场地上测，而且在它们打架时说出来。** `agents/bench3` 是我们自己的家族；
   `agents/ghosts` 是 156 条重放的天梯轨迹。它们已经在 produce 轴上相差七个名次 ——
   `mgtightgrain2` 在幽灵上排第一、在 `bench3` 上排第七 —— 而其中只有一个是关于天梯的
   证据。**只引用一个场地的数字，是一个关于那个场地的数字。**
8. **然后才提交。** 每天 5 次，最新两个活跃。

### 哪些对手值得花算力

一个对手的价值是它**跨候选的方差**，不是它的强弱。在一个引擎上用十个候选跑 7,296 局：

| 陪练 | 平均被赢 | 跨候选标准差 |
|---|---|---|
| `mgtightgrain2` | 64.6% | **29.7** |
| `orchardherd` | 73.4% | **26.1** |
| `rancher_rita` | 92.4% | 22.7 |
| `mgtight` | 39.8% | 20.8 |
| `melon_mateo` | 94.3% | 17.0 |
| `closer_cleo` | 0.3% | 0.7 |
| `ledger_lena` | 0.2% | 0.5 |
| `broker_bea` | 0.2% | 0.4 |
| `dairy` | **100.0%** | **0.0** |

`orchardherd` 很弱 —— 作为候选只有 36.5% —— 却是场地里第三有信息量的对手。
**弱和没用是两回事。** 没用的是 `dairy`：每个候选在每一局都赢它，均值 100.0%、
标准差精确为零。它已被移除。

剔掉 `dairy` 和三个 meta agent 后，候选排名**完全不变** —— 十个全部保持原位 ——
而算力省了 37%。

但要把 meta agent 留在场地里，并且**分开报告**。它们是另一端的饱和（我们赢 0.2%），
把它们平均进去只是加了一个常数：十五个对手里三个打不过，等于给每个头条数字压了
约 25 分，所谓「43%」的真实含义是「对能打的对手 73.5%，对三个打不过的 0%」。
**两个数字，不是一个。**

场地缺的是中间地带，而 `tools/lines.py --emit` 提供了它：`line1` 是天梯上跑得最多的
那条线，对这个场地是 66.6%，刚好在我们最好的引擎 60.9% 之上。

### 饱和有两端，我们刚撞上远的那端

`dairy` 被剔是因为每个候选每次都赢它。2026-08-11 出现了相反的情况：测量八个
`closer_cleo` 量级 agent 的变体时，**幽灵场地对其中七个返回 99.4%**，一个都分不开；
`bench3` 紧随其后 —— 同样这批臂在那里是 92–98%。

两个参考场地都是为了给**我们的**引擎排序而建的，而我们的引擎赢它们 54–61%。
它们在一个赢 98% 的 agent 那个层级上没有分辨率。

在那个层级唯一还能区分的场地，是**带外包装的 agent 互相打**：`closer_cleo` 92.7%、
`slotter_silas` 73.8%、`ledger_lena` 54.1%、`broker_bea` 29.3%，3,072 局 ——
间距干净，两端都不饱和。这个层级的任何测量都用那个面板，并在胜率饱和时把中位收入
当作次级信号（在幽灵胜率全部相同时，它仍然正确地给终局窗口扫描排了序）。

### 这个仓库反复上的两种当

**「它什么都没做，所以一定卡住了」。** 种子购买探针显示农场十天什么都没买、现金只有
$109–$435。它没卡住；它把现金花在牲畜上，而那更值钱。移除这个"死锁"在 137,664 局下
损失 8–14 分。**在判定引擎坏掉之前，先查清楚它把资源花到哪去了。** 代码里没有任何
地方写着"牲畜优先于种子" —— 那是一个现金下限和一个购买速率限制撞在一起的产物，
而**一个没有注释的正确行为，看起来和 bug 一模一样**。

**框架静默地跑了另一份代码。** `get_last_callable` 返回
`[v for v in env.values() if callable(v)][-1]` —— 模块字典里最后一个 callable。
包装一个 agent（`_INNER = agent`，然后重新 `def agent`）会让 `_INNER` 排最后，
于是框架加载的是**未包装**的那个，每个臂分数完全相同，而干净的结论是"这个改动毫无价值"。
在 `agent` 之后放一个辅助 `def` 后果相同。把 callable 存进列表、`del` 掉辅助名字，
然后**向加载出来的函数问一个已知答案的问题来验证** —— 能编译不等于对。
交接扫描有两个臂就是这样丢掉的，直到那个检查被写出来。

## 8. 吞吐参考

带 `KG_FAST_ENV=1` 时**每核每秒约 0.375 局**（该开关跳过 jsonschema 校验，
实测结果逐字节相同）。

| 配置 | 局/小时 |
|---|---|
| 1 核 | 约 1,350 |
| 8 核笔记本 | 约 10,800 |
| 32 核 | 约 43,000 |

一次有效力的 5 分 A/B（384 局）在八核笔记本上约 4 分钟。更大的跑数见
`docs/CONTRIBUTING.md`《在 Vulcan 集群上跑》，或者直接拿别人跑好的证据（`tools/sync.py import`）。

**锦标赛/评估负载是纯 CPU 的，不要为它申请 GPU**：单线程 Python，42% 的时间
花在框架内部的 `deepcopy` 上。RL 训练当前也默认 CPU，正式训练经
`tools/submit_rl.py`；只有有实测理由时才使用 `slurm/rl_train.sh` 的 H100。
**评估永远跑 CPU 参考引擎**，包括 RL 产物的评估。资源规则见 `docs/INFRA.md`。

# 怎么验收一个 RL 产物

`rl/README.md` 承诺"一切最终验收仍走本文档的规矩"，这一节就是那条链：

1. **训练期的数字不算数。** 批次 win 率随对手池采样震荡；定点 probe
   （固定种子 + argmax，`rl/probe.py`）是训练期唯一可比的曲线，且已与参考
   引擎评估校准（breach：probe −67,915 vs eval −67,270，`RUNS.md`）。
   它仍然只用于**训练内**决策（early stop、best.pt 棘轮）。
2. **验收 = 导出后在参考引擎上打十对手花名册。**
   `RUN=<run> CKPT=best.pt NAME=<语义名> sbatch slurm/rl_eval.sh` →
   `rl/eval_summary.py --run <run>` 出 Wilson 区间计分卡（每对手 96 局）。
   面板规矩（本文开头）原样适用：胜率是主量，margin 是"少输了多少"的辅量。
3. **提交门槛不因为它是 RL 而降低**：`SUBMISSION_POLICY.md` 全部规则适用，
   打包走 `tools/package.sh`（会带上 `weights.npz`），提交前 `stress.py` 28/28。
